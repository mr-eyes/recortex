# Optional active observation

The observer is experimental and off by default. It is one always-on note-taker of the conversation between you and the main session's agent, with several jobs: it keeps memories, a to-do list with checkmarks, the status summary and the copies of them (task lists, the board), and it drafts a change of the paper's text for you to accept. It reads what you and the agent said and the two dialogs you answered, and nothing else: your typed prompts, the agent's messages to you, the plan the agent showed in plan mode with your answer to it, and a question the agent asked with the option you chose. It reads no tool output, file contents, web page or command result, as evidence or as context, and never the plan file. From that conversation it selects the results and failures the agent reported to you, the decisions you stated in your own words or chose in a dialog, corrections, ideas, questions, the plans you agreed to, the steps the agent said are done and the items you asked to be reminded of. It records what was said; it does not judge the work itself or replace the agent's judgment. If the agent is misled, the record holds what you were told, which you saw and can correct.

Once you have chosen a level, nothing needs you in a normal session: the observer posts on its own within the level, and what it holds back for your answer the session asks you about, one multiple-choice question each (see [What waits for your answer](#what-waits-for-your-answer)). It runs only in a project folder that you enabled on this machine; repository trust alone does not enable it, and the project's shared configuration file cannot enable it anywhere. The ordinary briefs and manual recording workflow continue to work without it. A folder enabled with an earlier version (1.4.0 or before) is paused after the update: no hook captures, no worker runs and no model call is made until you answer the level question (the setup wizard's `observer-level`, or `observer.py enable --level L --yes`). The brief's setup line counts that question, and `hooks.py --doctor` and the status line say "recortex observer: paused until you choose a level."

GitHub remains the shared record. A private local queue holds work that is pending; queued, reviewed and posted are different states. A local capture receipt does not mean a result has reached GitHub. The queue is not a transcript backup: capture stores source pointers and hashes, and the native Claude transcript must still exist when a worker resolves them. Missing, changed or oversized sources defer work visibly. No lossless-session or exactly-once claim is made.

## Levels, tiers and caps

One setting, the level, per machine and project folder, kept with the observer's other settings in the private approvals file. The project file cannot set or raise it.

| Level | Runs on its own | Asks you first |
|---|---|---|
| Notes only | memories, the status summary | a held memory, as before |
| Assistant | the above, plus to-do items on an existing "To do" task, steps checked off, task lists and the hub's active list kept current, the reports | opening a task (the "To do" task too), closing a task, a held memory and every draft of the paper's text |
| Everything | all of the above, plus opening and closing tasks, the board and the sub-issue links | every draft of the paper's text, and a held memory |

At every level the paper's text is only proposed. In shadow mode nothing is posted, opened, closed or rendered at any level; reviewed events stay in the queue for the session.

Three tiers of model do the work, so that a cheap model sorts and a stronger one writes.

| Tier | Default model | What it does | Input per call |
|---|---|---|---|
| sort | `haiku` | reads each stretch of the conversation and labels what it holds, citing messages by number; it writes no record text | 32,000 characters |
| middle | `sonnet` | drafts a memory, a steps list or a mark from a label, and reviews each draft with a fresh call; refreshes the status summary | 48,000 characters |
| strong | none until you allow it, then `opus` | drafts a change of the paper's text, and reviews it with a fresh call | 120,000 characters |

Each distinct model has its own runtime check; a failed or changed check stops only its tier. A stopped sort tier stops the passes; a stopped strong tier stops only the manuscript keeper. A job that is not in your level is not drafted: a stretch whose labels all belong to jobs outside the level costs the sort call and no more.

Calls count against your Claude usage limits. The daily caps are per project, in a rolling 24 hours; the settings may lower them and never raise them (`observer.py limits [--sort N] [--middle N] [--strong N]`).

| Cap | Default |
|---|---|
| sort calls | 80 |
| middle calls | 70 |
| strong calls | 8 |
| tokens, input plus output: sort, middle, strong | 800,000, 700,000, 320,000 |
| candidates per draft | 6 |
| automatic comments | 25 a day |
| tasks opened | 3 a day |
| paper proposals | 2 a day |
| status summaries | 4 a day |
| task lists rendered by code | 30 a day |

A call is never cut short: a token budget stops the next call. A full cap leaves work queued, and the session is told once. A typical day is about 36 calls: 14 sort, 20 middle and 2 strong. These are calls, not money: no price applies under a subscription. When `ANTHROPIC_API_KEY` or a provider variable is set, the calls are billed there (see below).

## Enable and inspect

Run from the project root, using the installed skill's `scripts/` directory, in this order: enable in shadow mode with a level, check the runtime of each model, then switch to automatic mode if you want it. The setup wizard's question `observer-level` runs these steps for you (`setup.py observer --level L`, [setup.md](setup.md)); without the runtime check the observer takes notes but reviews nothing.

```bash
python3 scripts/observer.py status
python3 scripts/observer.py enable --level everything --model sonnet --sort-model haiku   # preview
python3 scripts/observer.py enable --level everything --model sonnet --sort-model haiku --yes   # 1. shadow mode
python3 scripts/observer.py runtime-check                            # 2. one check per distinct model; needs step 1
python3 scripts/observer.py enable --mode automatic --level everything --model sonnet --sort-model haiku --yes   # 3. optional
python3 scripts/observer.py pending
python3 scripts/observer.py limits --strong 4                        # lower a daily cap
python3 scripts/observer.py disable
```

`runtime-check` refuses until step 1 has recorded this folder's approval, because each check is bound to a model chosen there. Step 3 needs no terminal: the setup wizard's session switches automatic mode on after the user's answer to its question, as it records the field sheet's approval. The approval says where it was given, `session` or `terminal`; after a session switched automatic mode on, the next session start says so once, with the date: "recortex observer: automatic mode was switched on for this folder on <date> from a session; run observer.py disable in your own terminal to turn it off." The terminal steps that remain (`disable`, `release`, `resume`) guard against mistakes; they are not a security boundary (see "Task context and explicit holds").

`enable` requires `--model`, a Claude alias or model ID for the middle tier, and `--level` unless this folder's approval already holds one. `--sort-model` names the model that sorts (the middle model sorts when it is left out) and `--strong-model` the one that drafts the paper's text (the keeper stays off when it is left out; the setup question `paper-proposals` asks for it only in a project with a plan, a writing mode other than off and the level Assistant or Everything). Without `--yes` it previews the settings and says how the calls are counted: they run with `claude -p` under your Claude Code sign-in and count against your account's usage limits, at most 80 sort calls, 70 middle calls and 8 strong calls a day for the project, each tier with its own input limit. No dollar figure applies, and no saving is claimed. The calls use the environment as Claude Code does. When `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, a `CLAUDE_CODE_USE_*` provider variable or `AWS_BEARER_TOKEN_BEDROCK` is set, `enable` and `status` name it (never its value) and say that the calls are billed to that key or provider instead.

`--yes` records the settings for this project folder on this machine, in `observer-approvals.json` in the private state folder beside the user key. The entry binds the repository, the folder's real path, the exact settings and this machine's key-derived identity. Nothing is written to `.recortex.json`. A second checkout or worktree of the same repository needs its own `enable`, and a copied state folder does not carry an approval to another machine. The project file can only switch the observer off, with `"observer": false` (or an observer entry whose `"enabled"` is false); `status` then reports `project_switch: off`. That stops capture and posting, but not the holds, which stay in force while this folder has an entry on this machine. `disable` removes this folder's entry and leaves the queue and its holds; while a hold applies, it asks you to type `disable` on your own terminal, as `release` does.

Shadow mode, the default, reviews candidates without posting. Automatic posting requires `enable --mode automatic --model M --yes` after a successful `runtime-check`, which needs this folder's approval in shadow mode first and is bound to the installed Claude executable and the chosen model. Changing a model needs a new `enable` and a new runtime check of that model. The runtime check reports `requested_model`, the model Claude announced, the credential source Claude Code named (`api_key_source`) and any billing variables, and `status` keeps them under `runtime_last`. These controls do not edit your Claude account or global settings. See the [Claude CLI model and settings flags](https://code.claude.com/docs/en/cli-reference).

The runtime check must establish structured output, disabled tools and MCP, isolated settings, and absence of hook recursion. It requires that no tool, MCP server or skill is loaded; it records, but does not limit, the plugins Claude reports. If that proof is unavailable, captures remain queued and independent model checks do not run. Merely finding `claude` or passing a unit test does not establish runtime compatibility. Verify `status`; do not describe automatic operation as active when the gate is unavailable.

Capture also requires a safe native transcript path. The transcript and its project directory must belong to the current user, and every ancestor must belong to that user or root. Symlink components and world-writable paths are refused. Group write on a folder is accepted only for the owner's private group as the local files `/etc/passwd` and `/etc/group` define it: the owner's primary group, named after the owner, with no member but the owner, and no other local account's primary group; a network account or group, a file over 4 MiB or one with any line that does not parse cleanly (a NIS `+` or `-` entry included) is refused, and the system's own lookup must agree with the files. That is the default layout on Ubuntu, where `~/.claude` and `~/.claude/projects` are mode 775. A transcript file must always be writable by the user alone, and is read through a descriptor opened without following a symlink and checked again before every read. A sticky ancestor outside the source tree is allowed when owned by root or the current user, such as a trusted shared temporary directory. A directory's owner can replace its children even with mode `0755`.

`status` reports the metadata-only `capture_preflight` check, fixed reasons such as `source-permissions`, and boundary names such as `native-config`, `native-projects` or `ancestor`. `status --source-details` additionally displays the failing directory paths, modes and ownership, without reading any transcript contents or changing permissions. Review only those exact paths in your own terminal. For a confirmed directory owned by you that is not intentionally shared, `chmod go-w -- '/exact/reported/directory'` removes group/other write bits without changing read access. Do not run that placeholder literally, use recursive chmod, change another owner's directory, or change shared storage merely to bypass this check. Rerun the diagnostic afterwards. A failed check leaves capture unavailable; the observer does not alter Claude's files or directory permissions.

A user namespace or execution sandbox may expose a system ancestor's owner as an unmapped identity. The observer reports `source-owner`; it does not guess that an unknown owner is root. Repeat the diagnostic in the normal host terminal where ownership can be established. Do not change ownership of system directories to satisfy the check. Offline fixtures may explicitly simulate trusted system metadata, but that simulation does not establish real capture readiness.

```bash
python3 scripts/observer.py run-worker --dry-run
python3 scripts/observer.py context --query "pipe reader" --issue 7
python3 scripts/observer.py holds
python3 scripts/observer.py pause publication
python3 scripts/observer.py resume publication
python3 scripts/observer.py discard EVENTKEY
```

Pause and resume accept `capture`, `publication`, or `all`. A capture pause keeps established holds active. A pause is yours to lift: `resume` asks you to type `resume` on your own terminal. `record --source SOURCE_ID` retries an existing queued observation through the same review path; it does not accept arbitrary model-provided file paths. `reconcile EVENTKEY --dry-run` previews receipt reconciliation. `discard EVENTKEY` drops a ready or deferred event that will not be posted; its excerpts then expire with the retention. Status and pending output distinguish local backlog, deferred evidence, budget exhaustion, uncertain publication and verified receipts.

## Capture, review and publication

Command hooks collect bounded source descriptors from the native transcript: your typed prompts, a message you type while a turn runs (which Claude Code stores as a queued command from you, with no prompt record), the form Claude Code stores a typed `/recortex` command in (for holds only), a message from a chat channel such as Telegram (for holds only: another person can write in a channel, so it never counts as your words for a decision or a change of status, nor as a source), and the text blocks of the agent's messages. Two dialogs you answered are also read, from the main session's own transcript and matched by call id: the plan the agent showed in plan mode (its text, as the `ExitPlanMode` call carries it) with your answer, approved or rejected, and a question the agent asked with the option you chose (`AskUserQuestion`). Free text typed into a dialog ("Other"), feedback typed to a rejected plan and the plan file are never read, and a question of recortex's own (a held memory, a task, a draft or a setup question) is never a source. A dialog that Claude Code does not write in a shape recortex knows (seen in version 2.1.327) is dropped and counted as `dialogs_unread` in `status`. A dialog choice is weaker than typed words: it can back a steps list and a decision in the form `Chose "..." when asked "..."`, and never a change of status. Thinking, every other tool call and result, and subagents' transcripts are not collected. The hooks make no model or network calls themselves; at session start, at a stop and before compaction a hook can start the finite worker, which does. Claude Code writes a turn's final message after its Stop hook, so that worker first waits up to about 3 seconds for the transcripts it knows to stop growing, and reads their unread parts as a hook does; the transcript stays the only source. The worker waits for about eight sources, or for one that has waited ten minutes, so that a call sees a stretch of the session. A cursor and its descriptors commit together to the private state database. A transcript seen for the first time (the observer enabled in a long session, or one resumed later) is read from its last 32 MiB; the part left out is one source gap that `status` shows. Session and subagent starts also provide local context; prompts, Bash calls, stops and compaction provide collection opportunities. No observer hook runs after other tool calls or at a subagent's stop (the separate `SubagentStop` hook of the usage count reads numbers only; see Usage below). Before a Bash call, a synchronous transcript scan checks for original user controls. See the [Claude hook contracts](https://code.claude.com/docs/en/hooks).

The hooks are registered for everyone, and cost about 3 ms each when the observer is off: `run_observer_hook.sh` looks for this folder's real path in this machine's `observer-approvals.json` and starts no Python without it. When the project file says `"observer": false` (written so in `.recortex.json`), it starts Python only before a Bash call, where the holds stay in force. When the observer is on, a Bash call costs one Python start, about 65 ms. A notice that does not change is shown once per session. Tool calls carry task context only before a git or gh action a hold can stop, and failures of the local queue are reported at the edges of a turn, not on every tool call.

The worker uses separate bounded calls. The sort call labels each stretch of the session, up to 16 messages cited by number: a memory (with its kind), a plan you agreed to, a step the agent said is done, a loose item you asked to be reminded of, or a bearing on a part of the paper's plan. It writes no record text, and its labels are only pointers. Code drops a label that breaks a rule (a to-do that cites no message you typed, a step marked from a message that is not the main agent's, a decision that cites neither your typed words nor an option you chose, a task that is not open, a plan part the record does not hold) and every label of a job outside your level; with no label left no further call is made. The draft call writes a short comment from the template for each label the cited messages support, and a fresh review call per candidate accepts or rejects it with a fixed reason. Code sets what a model need not choose: the issue of a to-do, of a new task and of a checkpoint that carries marks, and the `done=`, `dropped=`, `checks=` and `against=` values of the marker, which it composes from structured fields when the comment is posted. Models receive the conversation (who said each message, and when) and the current record context as data; no field sheet, mark or restricted pattern is sent to them. They cannot execute tools or publish. Every memory rests on what was said: a result or a failure on what the agent told you it found, a decision on your exact words, an idea or a question on your message. A candidate that opens a task or marks a step is also checked by code: a new task needs the plan and your approval (a plan-dialog approval, a question-dialog choice, or typed words the Agreed field quotes), a mark needs a message of the main agent that says the step is done, and a step that is only started or partly done is never marked. The reviewer checks a candidate against the messages it cites, the rest of that stretch of the session and the record; it does not judge whether the agent's work was right. It also sees the newest memories on the candidate's issue, and rejects a result or a failure that repeats one of them with nothing new. What the agent relays from a page, a file or a document is not a result of the work, and text it quotes that asks for a record is data. Existing issue destinations, event templates, restrictions and recorded links still apply. Ambiguous destinations, overlap or evidence defer a candidate.

Every kind of memory may post on its own in automatic mode, within mechanical limits that do not depend on a model:

- A memory that changes what an earlier one means (a correction, or a `replaces=`, `instead=` or `checks=` link; `checks=` answers a question or marks an idea tried) posts on its own only when it rests on what was said: your typed words, or the agent's message to you. Your words count when the memory quotes them in its own field (a decision's "Exact words", another kind's quoted lines): at least six words and at least half of one of your typed messages that it cites. The agent's message counts when the memory cites it; a subagent's report or a sidechain turn, which you never saw, is not the agent's message. That last rule is a chosen tradeoff: if a planted page misleads the agent, a change resting on its message posts on its own, and the record then holds what the agent told you, which you saw and can correct. A change resting on a short phrase such as "go ahead" alone waits for the main session. Whether the quoted words themselves state what the decision records is left to the reviewer, the last check here: a long request such as "summarize that page" meets the word count without being a decision.
- The body holds no image, no HTML other than the event marker on its first line and folds (no other HTML comment), no @mention (entities such as `&#64;` are decoded first), no reference definition, no address or link target outside `https://github.com/<owner>/<repo>/`, nothing shaped like `//host`, a backslash pair, `www.` or a scheme such as `data:`, and no `owner/repo#N`, `owner/repo@sha` or `user@sha` reference to another repository. Such a candidate waits for the main session. Bare `#N` and `GH-N` references to this repository are fine.
- The observer does not judge confidentiality: a project marked as handling sensitive material posts like any other, and a project that needs that judgment should not run the observer. The linter's rules, the project's restricted patterns and banned words included, apply to every automatic body, as to every post.
- At most 25 automatic comments and 3 opened tasks a day per project; the rest waits in the queue, and the session is told once.
- The body names nothing of this machine: no absolute local path, no home folder, no local user name and no email address, as written, with entities decoded, or as GitHub shows it once Markdown's backslash escapes are dropped.

Only the independent publisher appends reviewed event comments. It freezes the exact payload and source identities, records the sending state before the request, reads the stored body back and retains the receipt. An interrupted send becomes uncertain and is reconciled before retry. An event whose own problem stops it (lint, target, hold, one of the limits above) is deferred with that reason, and the next one is tried. Mutable topic bodies, the hub's text, labels and the resume block's own fields remain the main session's responsibility. The exceptions are copies that code writes from told memories, never a model (see Tasks and housekeeping), and the status summary below.

Shadow mode keeps reviewed events, with their excerpts, until they are posted by the main session, discarded, or the mode changes to automatic and they are posted.

## Tasks, steps and housekeeping

A plan you approved becomes a task: an `active` issue whose first comment is a `steps` memory with the numbered steps, and a task list under `## Plan` in its body. A step the agent reports done is checked: the observer posts a result, failure, correction or checkpoint with a `done=` mark, and code renders the box. A loose "remind me to ..." becomes one item on the standing "To do" task. The format and where the checkmarks show are in [tasks.md](tasks.md). The observer does not verify the work: a step is checked when the agent says it is done, and a step that is only started, in progress or partly done ("all tests pass except two") is never checked.

After a pass that posted something, and once a day, under the worker's lock, code does the housekeeping, each step under its own cap and recorded as an act, with no model call:

1. brings the index up to date;
2. renders every open task whose list differs from the computed one and was not changed by hand (at most 30 renders a day);
3. closes a task whose steps are all done or dropped (Everything; at Assistant it asks you first, at Notes only never);
4. renders the hub's `## Active issues` section when the hub has that heading;
5. links the tasks it opened under their topic (Everything);
6. keeps the board current when this machine has one set up (Everything).

Steps 2 to 4 need the level Assistant or higher. A step that fails records its fixed reason and the rest go on. A box ticked or unticked by hand on GitHub is not believed: the next render would put it back, so code does not render that task, counts it, and the brief says so; the session then asks you whether to record it or put it back.

## The manuscript keeper

The owner's rule for the paper: text from the observer is a proposal for you to accept, never written on its own, and only when something notable changed. The keeper runs only when all of these hold: the project has a plan and a usable plan issue; this machine's writing mode is `review` or `autonomous` (off, not chosen or unreadable means nothing is drafted and no call is spent); the level is Assistant or Everything, in automatic mode with publication not paused; a strong model is set and its runtime check is valid; and something notable is due and stable.

Notable is decided by code from the index: a claim became backed since the part's newest text change; a memory the text rests on was corrected, replaced or set aside; a planned figure or table now exists (this joins a draft for the same topic, and alone only adds a line to the brief); or a claim is in doubt or the plan's message changed (a line only, never a draft). A part due only because of a new Methods decision is not notable. Stable means the part's material has been unchanged for 30 minutes, no source arrived for 10 minutes, the topic was not proposed in the last 24 hours, fewer than 2 proposals were made today and no draft for the topic waits; the keeper also leaves a topic alone for 2 hours after you started writing it from another folder.

The keeper runs `write.py start`, one strong call that drafts the whole body, a fresh strong call that reviews it, and `write.py check`, whose eight refusals are the last word. A draft that passes waits for your answer; one that fails is refused and not tried again until what it rests on changes. The worker never runs `write.py apply`. Your "Approve" is the approval, bound to the exact bytes you were shown: the recorded hashes of `draft.md`, `used.json` and `memory.json` are checked before the write, and a draft whose files changed is refused as stale. "Not now" asks again after 7 days; "Drop it" waits until what the part rests on changes. In autonomous mode the keeper's draft still waits. The way the session asks is in [writing.md](writing.md), "Drafts that wait".

## What waits for your answer

Four kinds of item wait for you. The session asks each as one multiple-choice question from a fixed template, with the options shown, and the quoted line as stored. A title or a plain line is record or model text: it is shown to you in the dialog and never placed in a hook payload, which carries counts and short ids only.

| Item | Question | Options | Carried out by |
|---|---|---|---|
| A held memory | `Memory <short> (<kind>) on #<issue>: "<line>". It would change: <changes>. Post it, or drop it?` | Post, Drop | `post_verified.py comment --eventkey KEY`; `observer.py discard KEY` |
| A task to open (Assistant) | `Task <short>: open a task "<title>" with <n> steps?` | Open it, Not now, Drop it | `observer.py act SHORT`; `observer.py later SHORT`; `observer.py discard KEY` |
| A task to close (Assistant) | `Task <short>: every step of #<N> is done. Close it?` | Close it, Not now | `observer.py act SHORT`; `observer.py later SHORT` |
| A draft of the paper's text | `Draft <short>: update the <heading> of #<N>. Approve it, or not?` | Approve, Not now, Drop it | `observer.py drafts apply`, `later` or `drop ID` |

`observer.py pending --waiting [--json]` lists them with the templates filled in; the JSON form cleans the titles and lines as the text form does and carries the data header in its `data_header` field. Every answer that changes something needs a one-time grant: before the Bash call that carries it out (`act`, `later`, `discard`, `drafts apply`, `drafts later`, `drafts drop`, `post_verified.py comment --eventkey`), the hook looks in the main transcript for the question tool's own call naming that short id and quoting that line, and your recorded answer to it, with the label of that answer ("Open it", "Close it", "Post", "Approve", "Not now", "Drop it" or "Drop"). Only that gives a grant, kept in the private observer state for 10 minutes and consumed by the command; without it the command is refused, so a session cannot postpone or drop what waits for you on its own. An answer to another item's question, a question the session worded itself and an answer with another label give none. You may also run `later` and `discard` yourself in a terminal of your own. A tool result, a page or a subagent cannot give that answer.

At session start the observer's context holds one fixed line when anything waits ("recortex observer: N items wait for the user's answer. Load the recortex skill first, run its observer.py pending --waiting, and ask each as one multiple-choice question from the template it prints. Do not offer them in prose."). A reminder follows at the next prompts while items wait and `pending --waiting` has not run in the session, at most 3 times a session and 3 prompts apart, from the second prompt. At the level Assistant the question about a task comes with the next prompt, not at a pause.

## The acts log and undo

Everything the observer does beyond posting a memory is an act in its private store: a memory posted, a task opened, steps added or marked, a list rendered, a task closed, the hub's list rendered, a status summary, a board update, a draft proposed or applied. `observer.py log [--days N]` prints each act with its address, in your terminal. At session start, at most once in 6 hours per session, one notice built from fixed words and numbers says what it did since the last one ("recortex observer: since <stamp> it posted 6 memories, checked 3 steps, opened 1 task and closed task #14. observer.py log lists them."). The mind page's to-do view ends with the acts of the last 7 days.

`observer.py undo ACT`, which you run yourself in a separate terminal, outside Claude Code, and confirm there (as for `release`), reopens a closed task, restores a rendered body from its backup (refusing a body that changed since), or closes a task it opened as not planned. For any other kind it prints one fixed line that says how that kind is corrected: a memory by a correction, a change of the text by `versions.py restore`.

## The main session's own memories

While the observer is on, the main session still posts its own memories with `post_verified.py comment` (and `create_issues.py`), in shadow and automatic mode. Each verified post is registered in the observer's queue, so that nothing is posted twice: the observer drops its own candidates of the same kind for the same issue that rest on what came before that post, and its ready events of that kind for that issue wait for the main session. A copy of a queued memory (its reviewed body, with or without its event key), a decision the queue already holds with the same exact words, and a change of status of the same memory (the same `replaces=`, `instead=` or `checks=` target) as a held event still waiting are refused with the event key: post that event with `--eventkey`, which keeps its holds and the session's withhold. Discarding an event posts nothing and does not lift this: a copy of a discarded event is not posted, and a discarded decision that was held (by a hold, the session's withhold, or the automatic gate; the queue marks it so for good) still blocks its exact words. The whole queue is searched, by digest; when the search cannot complete, the post is refused. A memory the session rewrites in its own words still posts. Two paths are the main session's own work and stay open: discarding a held event and then writing its own change of status, and a correction that names the memory only by its address.

To post a reviewed event, in automatic mode, use `observer.py pending` to find it and `observer.py pending --eventkey KEY --show-body` to display its reviewed body, then `post_verified.py comment --issue N --kind <kind> --body-file <that body> --eventkey KEY`. The issue, kind and draft must match the event exactly; the script uses the shared publisher and receipt, so retrying a verified event does not append another comment. The main session may post a deferred event this way after its own review, and the daily cap of automatic comments is not its. An event the automatic gate held back for your answer (a change of status that rests on neither your words nor the agent's message) is listed by `observer.py pending --held` (and, with the other items that wait, by `pending --waiting`); at the next session start, where the hook says how many items wait, the session asks you one multiple-choice question per memory, from a fixed template that names its short id, its kind and what it would change and quotes its plain line (or, for a body without one, its kind and the start of its first paragraph), with the options "Post" and "Drop", then posts it this way or drops it with `observer.py discard`. There is no terminal step, but the post is bound to your answer: before the Bash call that runs `post_verified.py --eventkey KEY`, the hook looks in the main transcript, read as capture reads it, for the question tool's own call in a main-session message naming that short id and quoting that line, so that you answered about that memory and not a description the session wrote, and the result Claude Code recorded for it, and only your "Post" there gives a one-time grant, kept in the private observer state for 10 minutes and consumed by the post. Without it the post is refused (`held_unanswered`) and the memory stays listed: ask again, and post right after a "Post". A tool result, a page or a subagent cannot give that answer; a session that writes the transcript or the grant file itself can, which is the limit stated for holds below. Its copy without `--eventkey` is refused, so it is posted only through that question. A session you kept off the record is not posted this way either (see below). The mechanical body limits still apply. These checks coordinate the repository's posting helpers; they do not intercept arbitrary `gh` commands or browser posts.

The first release binds approval and publishing to one installed machine per project folder. Several sessions on that machine share the queue and publisher lock. Automatic failover and distributed publishing are outside this contract. This is a single approved installation assumption, not distributed fencing: cloned user keys and machine identity can undermine that assumption. Do not copy an approval or its private state to another host. The approval does not name a GitHub account: the publisher posts as whichever allowed account `gh` uses.

## Task context and explicit holds

Task context uses the same allowed authors and memory interpretation as the mind page, ranked for the task and its thread. Recorded decisions, failures, support and replacements travel together. It preserves full selected fields, including qualifications and denominators; a group that cannot fit is omitted with a source pointer. Excluded support is identified without exposing its text. Resume text is rechecked against the current allowlist and matching unedited comment. The packet states its cache age and missing evidence. It is quoted data, never permission to act. A packet with the same selection is not repeated within a session.

Only a recognized whole original user message creates a local hold. Supported messages are:

```text
/recortex hold git-tag
/recortex hold git-push
/recortex hold gh-release
/recortex hold command EXACT_COMMAND
```

These hold the repository until released. A small set of whole phrases such as `don't push` or `do not tag` holds only the session it was typed in.

The user can also keep a session's moments off the record. A message that says `don't post`, `do not record`, `don't publish` or `off the record` anywhere in it holds the publication of that session's moments (a `publish` hold, which keeps only the phrase). The worker selects nothing from that session, so no call is spent on it, and the reviewer rejects such a moment with the reason `withheld`; an event of that session that is reviewed anyway is deferred as `withheld`. It is posted by no path, the main session's `--eventkey` included, until the user releases that hold with `observer.py release HOLD_ID` in their own terminal, which is the later, explicit request. The hold stops no command. The hook interprets the persisted original message, typed as plain text or in the form Claude Code stores for a typed `/recortex` command. Arbitrary natural language is not a policy parser. "Original user" means the user role in the transcript: in a session driven by the Agent SDK or `claude -p`, the host's message has that role, so a host that relays outside text can set a hold; a hold only denies.

Nothing in a session releases a hold: not a typed message, not a transcript line, nor a hook's input. A Bash call that names `observer.py` with `release`, `disable` or `resume` is always denied in a folder with an entry, whether or not a hold applies; the command is read as the shell splits it. These commands are the user's: `release`, `disable` while a hold applies, `resume` of a pause, and an `enable --yes` that replaces this folder's entry with one for another repository while the holds of the one it names apply, each ask on the user's own terminal and refuse without one. `"observer": false` in the project file switches the observer off but leaves its holds in force. To release one, run `python3 scripts/observer.py release HOLD_ID` yourself in a separate terminal, outside Claude Code (`observer.py holds` lists the ids). It asks you to type `release` on that terminal, and refuses when it has no terminal of its own, as with Claude Code's Bash tool. Compaction, elapsed time or omission from a summary releases nothing. Holds, pauses and these terminal confirmations are guards against mistakes, not a security boundary: they stop the model's direct commands, but a program run with your rights can still change your private files, reach `observer.py` under another name or delete the queue file, which lifts every hold. Do not rely on them against a session that is trying to get round them. A session with shell access can lift a hold or resume a pause through a pseudo-terminal or a command the checks do not recognize; they exist to stop accidental actions. The holds that apply are those of the repository this folder's entry on this machine names, whatever the project file says; when the approvals cannot be read, the check fails closed as for unreadable holds.

The local check can deny Bash calls for Git push, Git tag changes, GitHub release changes, and an exact command string. It looks at every simple command of the line: it splits on `;`, `&&`, `||`, `|`, `&` and newlines, leaves out redirections, leading variable assignments, shell keywords such as `if` and `do`, and wrappers such as `env`, `sudo` and `timeout`, and looks inside `bash -c` and `sh -c` strings, `eval`, `watch` and every `find -exec` group; `xargs git` and `xargs gh` count as every held action of that program, since their arguments come from stdin. Then a general rule: a simple command whose own words include all of a held action's words (`git` and `push`, `git` and `tag`, `gh` and `release`) is that action, whatever program starts it (`retry git push`), unless it is that action's read-only form run as the command's own program, its flag an option before any `--` (`git push --dry-run`, `git tag -l`, `gh release view`; `env git push --dry-run` is held). A line with ANSI-C or locale quoting (`$'...'`, `$"..."`) is not decoded: every held action counts as present. The words inside one quoted argument are one word, so `echo 'git push'` and a quoted commit message run; `git log --grep push` is held. A line it does not take apart (an unbalanced quote, a command or process substitution, a here-document, a subshell) is denied when it holds the held action's words, such as `git` and `push`. A wrong denial is accepted: you asked for the hold. `git -C <path>` counts as this repository, and a `gh` command whose `--repo` names another repository is not this repository's. Read-only commands such as `git status` and `git push --dry-run` go on. Shell aliases, scripts, programs run by other programs and other tools are outside the check. It does not enforce a universal shell policy. Ordinary context and advice never deny a tool, and an asynchronous warning cannot stop a completed action. The holds are read before each Bash call without the queue's locks. When they cannot be read at all, in a folder where the observer is on, every Bash command is denied with one fixed reason except `pwd`, `ls` and `cat` with plain path arguments and no option: the options of other reading programs can run another program, and git obeys the repository's config. The reason says that the user can see why with `observer.py status` in a separate terminal outside Claude Code; it names no way round the check. Whether a command typed at Claude Code's prompt with `!` passes through this hook is not established here, so the reason does not rely on it.

UserPromptSubmit can run before its transcript line is written and can represent an initiated turn rather than a person. Hook prompt text alone therefore cannot prove user authority. The check before a Bash call rescans persisted original sources; if those sources lag, a new hold may not yet be enforceable and a fixed warning says so. Check the acknowledged hold with `holds` before relying on enforcement. Existing Claude permissions remain in force.

Recognized explicit control quotes are a narrow local-storage exception: they are stored without model review so local enforcement can work, after mechanical secret and restricted-pattern checks. They are not sent to a model for classification. Narrative source text is not archived by capture. Independent review may retain the minimum evidence needed by a candidate; the reviewer must reject unnecessary sensitive text. Pattern checks and framing are limited defenses, not proof that arbitrary text is harmless.

## The status summary

The observer also keeps the project's status summary current, so that a session that never ends has one. In automatic mode, when the summary is stale by the brief's own rule (5 or more told memories since the newest resume block, or a day since it with at least one) and publication is not paused, the worker makes one more model call that writes only the "In short" paragraphs (two, at most 1,200 characters) from the index's told memories, the plan's integers and the recent typed prompts and agent messages it holds, a fresh call that reviews them (supported, no number the sources do not give, no secret, no address or issue number), and, only when both passed, posts a new resume block through `resume_block.py update` with the stamp "by the observer". Code writes the rest of the block from the index: the active issues with their step counts ("#14, 3 of 5 steps"), the next open step of up to 5 open tasks, and the 3 newest told decisions; the current focus and the holds are copied from the newest block word for word. At most 4 a day; both calls are counted in the middle tier's cap as the job `status`; a session the user kept off the record is left out of the sources; the hook shows no reminder while this is on. In shadow mode, or with publication paused, nothing is posted and the hook's reminder shows.

## Usage

What the plugin used is measured in tokens and calls, never money; under a subscription these count against your usage limits and no price applies.

- The observer's own background calls are exact: every call's tier, model, job (`sort`, `memories`, `status`, `paper`, `check`) and its input, output, cache-read and cache-write tokens are kept in the private store, which is also the ledger of the daily caps. Token columns are zeroed after 35 days.
- The plugin's own subagents (`recortex:record-auditor`, `record-drafter`, `record-reviewer`, `record-planner`, `record-planner-session` and `ask`) are exact for what their own transcript holds. A `SubagentStop` hook adds the four token counts and the model name to `usage.db` when one stops; it prints nothing, returns no context and runs under a 5 second limit.
- What the hooks add to your sessions' context is estimated: characters divided by 4, per event.
- The main session's own work on the record is not measured.

`usage.py show [--days 7|30] [--json]` prints the numbers in the terminal, and the mind page's last view, "What did recortex use?", shows them: today against each tier's caps, the last 7 and 30 days by tier and job, a bar for each day, the largest users of the week and the plugin's subagents. `usage.db` holds only integers, a tier, a job, an agent name from the fixed list, a model name and a day; rows older than 35 days are removed by the observer's daily cleanup. Expect about the same use as 1.4.0 (8 percent less by one weighting, 9 percent more by another): the gain is what gets recorded, not the cost.

## What you should still expect to do

The observer sees what is said in the chat, and nothing else.

- Work done outside Claude Code (a run on a cluster, a figure made by hand, a call with a coauthor) is not seen. Say it in the chat, or record it.
- A result the agent found and never stated is not seen. The session still states outcomes with their numbers, and its own recording stays in place; nothing is posted twice.
- A step is checked when the agent says it is done. The observer does not verify the work.
- It does not judge confidentiality; a project that needs that judgment should not run it.
- Numbers are kept as said. Evidence lines, figure blocks and Sources rows that need a file or a commit are the session's, as are bodies outside the plan, plan revisions and the author's questions.
- Answer what waits: drafts in review mode, held memories, tasks to open or close, boxes and cards changed by hand.
- Glance at the acts line. A wrong task or checkmark is one command to undo.

## Limits and recovery

Defaults are 80 sort calls, 70 middle calls and 8 strong calls per project in a rolling 24-hour window, with token budgets of 800,000, 700,000 and 320,000 (the table under Levels, tiers and caps), including failed calls, at most 32,000, 48,000 and 120,000 input characters per call by tier, six candidates per draft and 25 automatic comments a day. A failed sort or draft call is tried again after five minutes; a failed batch is offered again in halves, and a source that fails on its own stops after three attempts and stays in `pending`. The settings may lower those ceilings, never raise them. A full call cap or token budget leaves pending work queued and says so once. The default backlog cap is 128 MiB or 10,000 pending observations. Reaching a cap stops accepting new capture without advancing its cursor and leaves a persistent degraded status. Pending evidence is never silently expired.

The pending database lives under the private state directory, separate from the rebuildable index in the cache directory. It uses synchronous SQLite transactions, private permissions and checked paths. It must not be deleted as a cache repair. Corruption is reported; it is not silently reset. Reviewed excerpts of handled events become eligible for cleanup after seven days by default, configurable to a shorter interval; pending evidence is never silently expired. A finite worker checks cleanup daily while the plugin is active, including when capture is paused or the model runtime is unavailable. This is not a wall-clock retention daemon. Identity metadata, explicit holds and publication receipts remain, as do observation metadata (transcript paths, offsets and hashes), invocation times and hold quotes, all private with mode 0600. Native Claude transcript retention is managed by Claude, independently of this queue.

After interruption, inspect `status` and `pending`, restore source availability where possible, and reconcile uncertain sends before retrying. A verified receipt establishes the stored comment matched the frozen draft at read-back; it does not establish that the underlying research claim is true. Local queued work still needs review and publication before another machine can recover it from GitHub.

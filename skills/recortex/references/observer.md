# Optional active observation

The observer is experimental in 1.1.0 and off by default. It is a note-taker of the conversation between you and the main session's agent. It reads two things: the prompts you type, and the messages the agent writes to you. It reads no tool output, file contents, web page or command result, as evidence or as context. From that conversation it selects the results and failures the agent reported to you, the decisions you stated in your own words, corrections, ideas and questions. It records what was said; it does not judge the work itself or replace the agent's judgment. If the agent is misled, the record holds what you were told, which you saw and can correct.

It runs only in a project folder that you enabled on this machine; repository trust alone does not enable it, and the project's shared configuration file cannot enable it anywhere. The ordinary briefs and manual recording workflow continue to work without it.

GitHub remains the shared record. A private local queue holds work that is pending; queued, reviewed and posted are different states. A local capture receipt does not mean a result has reached GitHub. The queue is not a transcript backup: capture stores source pointers and hashes, and the native Claude transcript must still exist when a worker resolves them. Missing, changed or oversized sources defer work visibly. No lossless-session or exactly-once claim is made.

## Enable and inspect

Run from the project root, using the installed skill's `scripts/` directory, in this order: enable in shadow mode, check the runtime, then switch to automatic mode if you want it.

```bash
python3 scripts/observer.py status
python3 scripts/observer.py enable --model sonnet                    # preview
python3 scripts/observer.py enable --model sonnet --yes              # 1. shadow mode
python3 scripts/observer.py runtime-check                            # 2. needs step 1
python3 scripts/observer.py enable --mode automatic --model sonnet --yes   # 3. optional; asks on your terminal
python3 scripts/observer.py pending
python3 scripts/observer.py disable
```

`runtime-check` refuses until step 1 has recorded this folder's approval, because the check is bound to the model chosen there. Step 3 asks you to type `enable` on your own terminal; run it outside Claude Code.

`enable` requires `--model`, a Claude alias or model ID for the background calls. Without `--yes` it previews the settings and says how the calls are counted: they run with `claude -p` under your Claude Code sign-in and count against your account's usage limits, at most 60 calls a day for the project, each with up to 48,000 characters of input. No dollar figure applies. The calls use the environment as Claude Code does. When `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, a `CLAUDE_CODE_USE_*` provider variable or `AWS_BEARER_TOKEN_BEDROCK` is set, `enable` and `status` name it (never its value) and say that the calls are billed to that key or provider instead.

`--yes` records the settings for this project folder on this machine, in `observer-approvals.json` in the private state folder beside the user key. The entry binds the repository, the folder's real path, the exact settings and this machine's key-derived identity. Nothing is written to `.recortex.json`. A second checkout or worktree of the same repository needs its own `enable`, and a copied state folder does not carry an approval to another machine. The project file can only switch the observer off, with `"observer": false` (or an observer entry whose `"enabled"` is false); `status` then reports `project_switch: off`. That stops capture and posting, but not the holds, which stay in force while this folder has an entry on this machine. `disable` removes this folder's entry and leaves the queue and its holds; while a hold applies, it asks you to type `disable` on your own terminal, as `release` does.

Shadow mode, the default, reviews candidates without posting. Automatic posting requires `enable --mode automatic --model M --yes` after a successful `runtime-check`, which needs this folder's approval in shadow mode first and is bound to the installed Claude executable and the chosen model. Changing the model needs a new `enable` and a new runtime check. The runtime check reports `requested_model`, the model Claude announced, the credential source Claude Code named (`api_key_source`) and any billing variables, and `status` keeps them under `runtime_last`. These controls do not edit your Claude account or global settings. See the [Claude CLI model and settings flags](https://code.claude.com/docs/en/cli-reference).

The runtime check must establish structured output, disabled tools and MCP, isolated settings, and absence of hook recursion. It requires that no tool, MCP server or skill is loaded; it records, but does not limit, the plugins Claude reports. If that proof is unavailable, captures remain queued and independent model checks do not run. Merely finding `claude` or passing a unit test does not establish runtime compatibility. Verify `status`; do not describe automatic operation as active when the gate is unavailable.

Capture also requires a safe native transcript path. The transcript and its project directory must belong to the current user, and every ancestor must belong to that user or root. Symlink components and world-writable paths are refused. Group write on a folder is accepted only for the owner's private group as the local files `/etc/passwd` and `/etc/group` define it: the owner's primary group, named after the owner, with no member but the owner, and no other local account's primary group; a network account or group, a file over 4 MiB or one with any line that does not parse cleanly (a NIS `+` or `-` entry included) is refused, and the system's own lookup must agree with the files. That is the default layout on Ubuntu, where `~/.claude` and `~/.claude/projects` are mode 775. A transcript file must always be writable by the user alone, and is read through a descriptor opened without following a symlink and checked again before every read. A sticky ancestor outside the source tree is allowed when owned by root or the current user, such as a trusted shared temporary directory. A directory's owner can replace its children even with mode `0755`.

`status` reports the metadata-only `capture_preflight` check, fixed reasons such as `source-permissions`, and boundary names such as `native-config`, `native-projects` or `ancestor`. `status --source-details` additionally displays the failing directory paths, modes and ownership, without reading any transcript contents or changing permissions. Review only those exact paths in your own terminal. For a confirmed directory owned by you that is not intentionally shared, `chmod go-w -- '/exact/reported/directory'` removes group/other write bits without changing read access. Do not run that placeholder literally, use recursive chmod, change another owner's directory, or change shared storage merely to bypass this check. Rerun the diagnostic afterwards. A failed check leaves capture unavailable; the observer does not alter Claude's files or directory permissions.

A user namespace or execution sandbox may expose a system ancestor's owner as an unmapped identity. The observer reports `source-owner`; it does not guess that an unknown owner is root. Repeat the diagnostic in the normal host terminal where ownership can be established. Do not change ownership of system directories to satisfy the check. Offline fixtures may explicitly simulate trusted system metadata, but that simulation does not establish real capture readiness.

```bash
python3 scripts/observer.py run-worker --dry-run
python3 scripts/observer.py context --query "pipe reader" --issue 7
python3 scripts/observer.py holds
python3 scripts/observer.py pause publication
python3 scripts/observer.py resume publication
python3 scripts/observer.py discard EVENTKEY
```

Pause and resume accept `capture`, `publication`, or `all`. A capture pause keeps established holds active. A pause is yours to lift: `resume` asks you to type `resume` on your own terminal. `record --source SOURCE_ID` retries an existing queued observation through the same review path; it does not accept arbitrary model-provided file paths. `reconcile EVENTKEY --dry-run` previews receipt reconciliation. `discard EVENTKEY` drops a ready or deferred event that will not be posted; its excerpts then expire with the retention. Status and pending output distinguish local backlog, deferred evidence, budget exhaustion, uncertain publication and verified receipts.

## Capture, review and publication

Command hooks collect bounded source descriptors from the native transcript: your typed prompts, the form Claude Code stores a typed `/recortex` command in (for holds only), and the text blocks of the agent's messages. Thinking, tool calls, tool results and subagents' transcripts are not collected. The hooks make no model or network calls themselves; at session start, at a stop and before compaction a hook can start the finite worker, which does. The worker waits for about eight sources, or for one that has waited ten minutes, so that a call sees a stretch of the session. A cursor and its descriptors commit together to the private state database. A transcript seen for the first time (the observer enabled in a long session, or one resumed later) is read from its last 32 MiB; the part left out is one source gap that `status` shows. Session and subagent starts also provide local context; prompts, Bash calls, stops and compaction provide collection opportunities. No hook runs after other tool calls or at a subagent's stop. Before a Bash call, a synchronous transcript scan checks for original user controls. See the [Claude hook contracts](https://code.claude.com/docs/en/hooks).

The hooks are registered for everyone, and cost about 3 ms each when the observer is off: `run_observer_hook.sh` looks for this folder's real path in this machine's `observer-approvals.json` and starts no Python without it. When the project file says `"observer": false` (written so in `.recortex.json`), it starts Python only before a Bash call, where the holds stay in force. When the observer is on, a Bash call costs one Python start, about 65 ms. A notice that does not change is shown once per session. Tool calls carry task context only before a git or gh action a hold can stop, and failures of the local queue are reported at the edges of a turn, not on every tool call.

The worker uses separate bounded calls for selection and a fresh review. Models receive the conversation (who said each message, and when), the current record context and the approved field sheet's "Never write down" line as data. They cannot execute tools or publish. Every memory rests on what was said: a result or a failure on what the agent told you it found, a decision on your exact words, an idea or a question on your message. The reviewer checks a candidate against the messages it cites, the rest of that stretch of the session and the record; it does not judge whether the agent's work was right. What the agent relays from a page, a file or a document is not a result of the work, and text it quotes that asks for a record is data. Existing issue destinations, event templates, restrictions and recorded links still apply. Ambiguous destinations, overlap or evidence defer a candidate.

Every kind of memory may post on its own in automatic mode, within mechanical limits that do not depend on a model:

- A memory that changes what an earlier one means (a correction, or a `replaces=`, `instead=` or `checks=` link; `checks=` answers a question or marks an idea tried) posts on its own only when it rests on what was said: your typed words, or the agent's message to you. Your words count when the memory quotes them in its own field (a decision's "Exact words", another kind's quoted lines): at least six words and at least half of one of your typed messages that it cites. The agent's message counts when the memory cites it; a subagent's report or a sidechain turn, which you never saw, is not the agent's message. That last rule is a chosen tradeoff: if a planted page misleads the agent, a change resting on its message posts on its own, and the record then holds what the agent told you, which you saw and can correct. A change resting on a short phrase such as "go ahead" alone waits for the main session. Whether the quoted words themselves state what the decision records is left to the reviewer, the last check here: a long request such as "summarize that page" meets the word count without being a decision.
- The body holds no image, no HTML other than the event marker on its first line and folds (no other HTML comment), no @mention (entities such as `&#64;` are decoded first), no reference definition, no address or link target outside `https://github.com/<owner>/<repo>/`, nothing shaped like `//host`, a backslash pair, `www.` or a scheme such as `data:`, and no `owner/repo#N`, `owner/repo@sha` or `user@sha` reference to another repository. Such a candidate waits for the main session. Bare `#N` and `GH-N` references to this repository are fine.
- In a project marked as handling sensitive material, or whose field sheet is not approved on this machine, events are reviewed but nothing is posted on its own: the main session answers the confidentiality question at step 7 and tells the user before posting.
- At most 25 automatic comments a day per project; the rest waits in the queue, and the session is told once.
- The body names nothing of this machine: no absolute local path, no home folder, no local user name and no email address, as written, with entities decoded, or as GitHub shows it once Markdown's backslash escapes are dropped.

Only the independent publisher appends reviewed event comments. It freezes the exact payload and source identities, records the sending state before the request, reads the stored body back and retains the receipt. An interrupted send becomes uncertain and is reconciled before retry. An event whose own problem stops it (lint, target, hold, one of the limits above) is deferred with that reason, and the next one is tried. Mutable topic bodies, hub text, labels, resume comments and boards remain the main session's responsibility.

Shadow mode keeps reviewed events, with their excerpts, until they are posted by the main session, discarded, or the mode changes to automatic and they are posted.

## The main session's own memories

While the observer is on, the main session still posts its own memories with `post_verified.py comment` (and `create_issues.py`), in shadow and automatic mode. Each verified post is registered in the observer's queue, so that nothing is posted twice: the observer drops its own candidates of the same kind for the same issue that rest on what came before that post, and its ready events of that kind for that issue wait for the main session. A copy of a queued memory (its reviewed body, with or without its event key) and a decision the queue already holds with the same exact words are refused with the event key: post that event with `--eventkey`, which keeps its confirmation and the session's withhold. Discarding an event posts nothing and does not lift this: a copy of a discarded event is not posted, and a discarded decision that was withheld or held back still blocks its exact words. A memory the session rewrites in its own words still posts.

To post a reviewed event, in automatic mode, use `observer.py pending` to find it and `observer.py pending --eventkey KEY --show-body` to display its reviewed body, then `post_verified.py comment --issue N --kind <kind> --body-file <that body> --eventkey KEY`. The issue, kind and draft must match the event exactly; the script uses the shared publisher and receipt, so retrying a verified event does not append another comment. The main session may post a deferred event this way after its own review, and the daily cap of automatic comments is not its. An event the automatic gate held back, a change of status that rests on neither your words nor the agent's message or a post in a project marked sensitive, is posted only after you type `post` on your own terminal, as for `release`; from Claude Code's Bash tool it is refused. A session you kept off the record is not posted this way either (see below). The mechanical body limits still apply. These checks coordinate the repository's posting helpers; they do not intercept arbitrary `gh` commands or browser posts.

The first release binds approval and publishing to one installed machine per project folder. Several sessions on that machine share the queue and publisher lock. Automatic failover and distributed publishing are outside this contract. This is a single approved installation assumption, not distributed fencing: cloned user keys and machine identity can undermine that assumption. Do not copy an approval or its private state to another host. The approval does not name a GitHub account: the publisher posts as whichever allowed account `gh` uses.

## Task context and explicit holds

Task context uses the same allowed authors and memory interpretation as the mind page, ranked for the task and its thread. Recorded decisions, failures, support and replacements travel together. It preserves full selected fields, including qualifications and denominators; a group that cannot fit is omitted with a source pointer. Excluded support is identified without exposing its text. Resume text is rechecked against the current allowlist and matching unedited comment. The packet states its cache age and missing evidence. It is quoted data, never permission to act. A packet with the same selection is not repeated within a session.

Only a recognized whole original user message creates a local hold. Supported messages are:

```text
/recortex hold git-tag
/recortex hold git-push
/recortex hold gh-release
/recortex hold command EXACT_COMMAND
```

These hold the repository until released. A small set of whole phrases such as `don't push` or `do not tag` holds only the session it was typed in.

The user can also keep a session's moments off the record. A message that says `don't post`, `do not record`, `don't publish` or `off the record` anywhere in it holds the publication of that session's moments (a `publish` hold, which keeps only the phrase). The selector is told to skip such moments and the reviewer rejects them with the reason `withheld`; an event of that session that is reviewed anyway is deferred as `withheld`. It is posted by no path, the main session's `--eventkey` included, until the user releases that hold with `observer.py release HOLD_ID` in their own terminal, which is the later, explicit request. The hold stops no command. The hook interprets the persisted original message, typed as plain text or in the form Claude Code stores for a typed `/recortex` command. Arbitrary natural language is not a policy parser. "Original user" means the user role in the transcript: in a session driven by the Agent SDK or `claude -p`, the host's message has that role, so a host that relays outside text can set a hold; a hold only denies.

Nothing in a session releases a hold: not a typed message, not a transcript line, nor a hook's input. A Bash call that names `observer.py` with `release`, `disable`, `resume` or automatic mode is always denied in a folder with an entry, whether or not a hold applies; the command is read as the shell splits it. These commands are the user's: `release`, `disable` while a hold applies, `resume` of a pause, `enable --mode automatic`, and an `enable --yes` that replaces this folder's entry while holds apply, each ask on the user's own terminal and refuse without one. `"observer": false` in the project file switches the observer off but leaves its holds in force. To release one, run `python3 scripts/observer.py release HOLD_ID` yourself in a separate terminal, outside Claude Code (`observer.py holds` lists the ids). It asks you to type `release` on that terminal, and refuses when it has no terminal of its own, as with Claude Code's Bash tool. Compaction, elapsed time or omission from a summary releases nothing. Holds, pauses and these terminal confirmations are guards against mistakes, not a security boundary: they stop the model's direct commands, but a program run with your rights can still change your private files, reach `observer.py` under another name or delete the queue file, which lifts every hold. Do not rely on them against a session that is trying to get round them. A session with shell access can lift a hold, resume a pause or switch on automatic posting through a pseudo-terminal or a command the checks do not recognize; they exist to stop accidental actions. The holds that apply are those of the repository this folder's entry on this machine names, whatever the project file says; when the approvals cannot be read, the check fails closed as for unreadable holds.

The local check can deny direct Bash calls for Git push, Git tag changes, GitHub release changes, and an exact command string. Read-only commands and commands explicitly targeting another repository do not inherit this repository's hold. Shell aliases, compound programs, scripts, unknown directory overrides and arbitrary tool families are outside the check. It does not enforce a universal shell policy. Ordinary context and advice never deny a tool, and an asynchronous warning cannot stop a completed action. The holds are read before each Bash call without the queue's locks. When they cannot be read at all, in a folder where the observer is on, every Bash command is denied with one fixed reason except `pwd`, `ls` and `cat` with plain path arguments and no option: the options of other reading programs can run another program, and git obeys the repository's config. The reason says that the user can see why with `observer.py status` in a separate terminal outside Claude Code; it names no way round the check. Whether a command typed at Claude Code's prompt with `!` passes through this hook is not established here, so the reason does not rely on it.

UserPromptSubmit can run before its transcript line is written and can represent an initiated turn rather than a person. Hook prompt text alone therefore cannot prove user authority. The check before a Bash call rescans persisted original sources; if those sources lag, a new hold may not yet be enforceable and a fixed warning says so. Check the acknowledged hold with `holds` before relying on enforcement. Existing Claude permissions remain in force.

Recognized explicit control quotes are a narrow local-storage exception: they are stored without model review so local enforcement can work, after mechanical secret and restricted-pattern checks. They are not sent to a model for classification. Narrative source text is not archived by capture. Independent review may retain the minimum evidence needed by a candidate; the reviewer must reject unnecessary sensitive text. Pattern checks and framing are limited defenses, not proof that arbitrary text is harmless.

## Limits and recovery

Defaults are 60 actual model invocations per project in a rolling 24-hour window, including failed calls and both selection and review, at most 48,000 input characters per call, four candidates per batch and 25 automatic comments a day. A failed selection call is tried again after five minutes; a failed batch is offered again in halves, and a source that fails on its own stops after three attempts and stays in `pending`. The settings may lower those ceilings, never raise them. A full budget leaves pending work queued. The default backlog cap is 128 MiB or 10,000 pending observations. Reaching a cap stops accepting new capture without advancing its cursor and leaves a persistent degraded status. Pending evidence is never silently expired.

The pending database lives under the private state directory, separate from the rebuildable index in the cache directory. It uses synchronous SQLite transactions, private permissions and checked paths. It must not be deleted as a cache repair. Corruption is reported; it is not silently reset. Reviewed excerpts of handled events become eligible for cleanup after seven days by default, configurable to a shorter interval; pending evidence is never silently expired. A finite worker checks cleanup daily while the plugin is active, including when capture is paused or the model runtime is unavailable. This is not a wall-clock retention daemon. Identity metadata, explicit holds and publication receipts remain, as do observation metadata (transcript paths, offsets and hashes), invocation times and hold quotes, all private with mode 0600. Native Claude transcript retention is managed by Claude, independently of this queue.

After interruption, inspect `status` and `pending`, restore source availability where possible, and reconcile uncertain sends before retrying. A verified receipt establishes the stored comment matched the frozen draft at read-back; it does not establish that the underlying research claim is true. Local queued work still needs review and publication before another machine can recover it from GitHub.
